# Design doc (step 5)

Keep it concise: plain words, one fact per line, and nothing the code, the doc comments or a diagram already says. Cut any line a reviewer doesn't need to agree on the contracts. No page cap, but cap each step: one short line, then sub-bullets for cases. Sections in this order. Skip a section that doesn't apply (no UI, no stored state, no workflow, no new data) and say so in one line where it would be, so the reader knows it wasn't forgotten. If the feature spans repos, open one PR 0 per repo and keep the doc in the repo that owns the flow; the others link to it.

- **Bottom line** (unnumbered, above everything). One bold sentence: what the feature does, for whom, and the one decision the reviewer must agree on. A reader who stops here knows what PR 0 asks for.
- **Terms** (unnumbered, first after the bottom line). One line each for the nouns the doc uses: what is stored, the external objects, each workflow or job, and any state word such as "active". Use the repo's `GLOSSARY.md` words where they exist, and add new terms to it (`domain-modeling`). One meaning per word: if one verb would cover two different actions, give each its own word and define both.
- **1. User stories.** First line: who may act. Then one bold "As a user I want to ..., so that ...." per user action. If the one who acts is not a customer, name the role: "As an on-call engineer", "As a calling service". Bullets under each say only what that user sees and gets: input rules, page or message text in quotes, timing, what they can and can't undo. No HTTP codes, workflow names or table names.
- **2. Overview of the solution.** 5 to 8 bullets: which service owns which part, what each user action writes, how a change reaches other systems, how long-running or delayed work is triggered, what is out of scope.
- **3. States.** A state diagram of what the user sees or what is stored, then a table: each state, the stored values behind it, what the user sees, and anything else that changes with it (for example whether data flows). Name the function that picks the state.
- **4. Data model.** Each new or changed store (table, bucket, topic, cache key) and the name of the migration a later PR adds. For a table: column, type, null, default, written by. Then each repository method in one line: what it writes or reads, its guard, what it returns.
- **5. Architecture.** A flowchart of the services, stores, workflow engine and external systems, grouped by where they run. Edge labels name the transport (public route, private route, signal, auth method). 1 to 2 bullets on boundaries: who may reach what, and who never touches which store.
- **6. The core loop** (for example "Sync pass"), if a workflow runs in rounds. A flowchart of one round, the function and file that hold it, and bullets: what happens when triggers repeat or arrive during a round, what never triggers a destructive step, retry counts.
- **7, 8, ... One sequence per trigger**: each user action, and each schedule, event or caller that starts the flow on its own. A sequence diagram with `autonumber`, then a numbered list with the same numbers. Each item: one short line for the step, then sub-bullets for its failure cases, races, and what is left after a partial failure. Decisions and corner cases go into the step they affect, with their reason in one clause; there is no separate corner-cases or design-notes section. Every step that can't be undone (drop, delete, revoke access, send to a customer) says whether it runs at once, waits, or can be cancelled. Each business rule names its one owner (a package or function).
- **Contracts.** One table: name, caller, what (one short line), input, output, errors, owner package. Public routes, private routes, RPCs, signals, schedules, events and messages, CLI commands. For a signal or message, "what" says what happens when it arrives during a run and when several arrive at once. One row per contract. If it isn't obvious where internal entry points are served, say it in a line under the table.
- **Packages.** A mermaid graph. Put shared contract packages in their own subgraph, declared first, or mermaid moves them into another box. Solid arrows are imports and must point inward; mark an outward one as a defect. Check every solid arrow on the PR 0 code (`go list -f '{{.Imports}}'` in Go, the import lines elsewhere); never draw from memory. An import a later PR adds gets a `-- PR n -->` label. Dashed arrows are "implements" (label a later one with its PR). A one-line legend under it.
- **Security.** One bullet each, for those that apply: public entry points (who may call, what is and isn't checked), internal entry points (auth, network policy, what a caller inside the cluster could do), customer isolation, credentials, injection (SQL, shell, templates). Each says what is built, the gap if any, and the fix (link the open question).
- **Open questions** (last). Grouped by topic under bold labels. Each is a real question ending in "?", then "Built:" or "Proposed:" with the current answer, so a reviewer can say yes or no. Include what only the real external system can answer, each with the PR that tests it, and hidden dependencies on other features (for example "needs data loaded first").

Writing rules:

- Plain words, short sentences, one idea each. A type or function name only where it is the term.
- No dates, and don't describe the current system as "today" or "after this deploys". Refer to PR numbers, so nothing goes stale. Words that are part of the feature ("today's spend" in a daily budget) are fine, and so are dates the repo's doc rules require in front matter.
- Link to sections inside the doc instead of repeating a fact.
- Before handing over, check every claim (page text, limits, retry counts, status codes, route paths, schedule) against the code.
